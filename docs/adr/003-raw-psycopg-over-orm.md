# ADR-003: Raw psycopg3 on the write path, not an ORM

**Status:** accepted · **Date:** 2026-10-15

## Context

The processor writes batches of a few hundred enriched events at a time, and
the write path is the pipeline's throughput ceiling. SQLAlchemy's ORM,
SQLAlchemy Core, and raw psycopg3 were all candidates.

## Decision

Raw psycopg3 with a `ConnectionPool` for all runtime reads and writes. The
schema lives in hand-written Alembic migrations. No ORM models.

## Why

**Batch shape is the whole performance story.** One multi-row `INSERT` per
batch over a pooled connection is roughly an order of magnitude fewer round
trips than per-row ORM flushes, and the difference shows up directly in
`transitpulse.sink.write.duration`.

**The conflict semantics are not expressible in portable ORM terms.** Two
different strategies are needed in the same transaction:
`ON CONFLICT DO NOTHING` on the history (so replays are no-ops, and the
`rowcount` difference *is* the dedup metric), and
`ON CONFLICT DO UPDATE ... WHERE excluded.event_time > vehicle_live.event_time`
on the serving table (so a late stale ping cannot move a vehicle backwards in
time). Writing these as literal SQL makes the intent legible; expressing them
through a dialect-specific ORM escape hatch does not.

**Debuggability.** The SQL in the source is the SQL in `pg_stat_statements`.
During a load test that is the difference between finding the slow statement in
a minute and reverse-engineering generated SQL.

**There are no object graphs here.** Events are flat, immutable, and never
lazily traversed. An ORM's value — identity mapping, relationship loading,
change tracking — has nothing to act on.

## Consequences

- No autogenerated migrations. Accepted, and partly a benefit: declarative
  partitioning and partial indexes are things Alembic cannot reflect anyway, so
  autogenerate would have silently dropped them.
- SQL is Postgres-specific. Accepted; Cloud SQL is a deliberate choice, not an
  accident.
- SQLAlchemy remains a dependency, used only by Alembic for migration
  ordering and connection handling.
- Query construction must stay parameterised by hand. Enforced by ruff's
  bandit rules (`S`), which flag string-interpolated SQL.
